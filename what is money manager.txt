## Current architecture, backend, business rules, UI system, known fixes, and development rules

# 1. PROJECT OVERVIEW

Money Manager is a Flutter financial-management application intended to support multiple Businesses and multiple users inside each Business.

Main capabilities include:

* Authentication
* User profiles
* Multiple Businesses per account
* Business creation
* Business invitations
* Members and roles
* Business switching
* Transactions
* Transfers
* Money Holders
* Debts
* Receivables
* Debt payments
* Receivable collections
* Assets
* Dashboard financial summaries
* Audit/activity logging
* Actor attribution (“Created by …”)
* Settings / Light and Dark mode

The application is designed around this hierarchy:

```text
ACCOUNT
   ↓
BUSINESSES
   ↓
CURRENT BUSINESS
   ↓
BUSINESS-SCOPED FINANCIAL DATA
```

An authenticated user can belong to MULTIPLE Businesses.

`activeBusinessId` is only a pointer to the currently selected Business.

It is NOT the user's permanent Business ID.

# 4. WHY DENO EXISTS

Originally some trusted operations were implemented/planned with Firebase Cloud Functions.

The project then hit an important constraint:

Firebase Functions deployment required the Blaze/pay-as-you-go plan.

Because paid Firebase Functions were not an acceptable dependency, a Deno backend was created as an alternative.

A Deno proof-of-concept was first tested successfully for:

```text
/health
/auth-check
Firestore read/write
Firebase token validation
```

It was then expanded into the actual production backend.

Therefore:

**Deno is not just an experiment anymore.**

It currently handles important production Business/member/invitation/activity/identity operations.

Do not move functionality back to Firebase Functions unless explicitly requested.

# 29. GENERIC UID ACTOR RESOLVER

Originally, actor resolution outside Activity was transaction-specific.

There was a transaction resolver path such as:

```text
transactionActorNamesProvider
→ resolveTransactionActors(...)
→ transaction actor resolver endpoint
```

This was later generalized.

A shared UID-based actor resolver was implemented so financial screens can resolve:

```text

→ actor display name
```

The shared resolver is reused for financial attribution.

Do NOT recreate one resolver per feature.

---

# 30. IMPORTANT ACTOR RESOLVER AUTHORIZATION FIX

The generic actor resolver initially required:

```text
members.read
```

That caused normal active Business members to receive denied lookups, which the UI incorrectly surfaced as:

```text
Unknown member
```

This was fixed.

The resolver now requires the requesting user to be an:

```text
active Business member
```

rather than requiring team-management/member-reading permission.

Important distinction:

The REQUESTING USER must have active Business membership.

Do NOT require the historical actor himself to still be an active member, otherwise old records from removed members could become impossible to identify.

---

# 31. IMPORTANT RIVERPOD ACTOR PROVIDER FIX

A subtle Riverpod bug occurred.

Financial rows were doing something like passing a freshly created:

```dart
List<String>
```

to a family/provider every rebuild.

Because list identity changed, Riverpod treated it as a different provider instance repeatedly.

Result:

```text
Unknown member
→ one second later actual name
```

or persistent loading/fallback behavior.

This was fixed by giving the actor-name provider a stable canonical key rather than unstable new List identity.

Do not regress this.

# 33. “UNKNOWN MEMBER” LOADING STATE

If a financial page briefly shows:

```text
Unknown member
```

before changing to the real name, first distinguish:

```text
loading state
```

from:

```text
genuine unresolved identity
```

Do NOT use “Unknown member” merely because the async provider is still loading.

Preferred behavior is:

* hide attribution while loading, or use subtle placeholder
* show cached/resolved name when available
* show `Unknown member` only when resolution actually completes without identity

Do not immediately change backend if names appear correctly after loading.

# 59. WINDOWS REMOTE CONFIG ISSUE

A Windows native C++ assertion/crash was traced to Firebase Remote Config.

The final mitigation:

**return before ANY Remote Config access on Windows.**

Not just before `fetchAndActivate`.

Do not allow FirebaseRemoteConfig initialization/access on Windows in that service.

There were also Windows certificate-revocation security alerts related to this HTTPS behavior.

Do NOT disable:

```text
TLS validation
certificate validation
certificate revocation checking
```

as a workaround.

# 60. RIVERPOD STATE RULE

Be very careful when using Riverpod `.family` providers with:

```text
List
Map
Set
```

arguments created inside `build()`.

New collection identities can cause provider recreation.

Prefer stable/canonical provider keys or immutable equality-safe parameters.

This already caused the actor-name bug described earlier.

# 63. ACTIVITY / AUDIT SECURITY

Canonical identity is based on authenticated UID and trusted profile data.

Do not let clients arbitrarily submit:

as authoritative audit identity.

Store UID / trusted audit metadata and resolve the display identity.

# 69. HOW TO HANDLE A BUG

For a bug:

Do NOT start with:

```text
audit the entire repository and find best architecture
```

Instead:

1. Read the exact error.
2. Identify the likely file/class.
3. Inspect only that file and directly related dependency.
4. Fix the actual cause.
5. Stop.

Example:

A Riverpod `ConsumerWidget` must use:

```dart
Widget build(BuildContext context, WidgetRef ref)
```

while a `ConsumerState` / `State` build method uses:

```dart
Widget build(BuildContext context)
```

because `ConsumerState` already has `ref`.

This exact issue previously occurred in:

```text
transfers_page.dart
```

Do not repeat it.


Start with shared UI components only if the issue is genuinely shared.

Do not change 10 feature files when one shared component can safely solve the issue.

But also do not blindly modify a shared component if it could regress accepted screens.

# 71. HOW TO HANDLE BACKEND CHANGES

Before modifying Deno:

Determine:

```text
Does Flutter currently call this Deno endpoint?
Is there already a repository abstraction?
Does this change require production deploy?
Does Firestore already provide this feature directly?
```

After changing production Deno behavior, remember:

```powershell
deno deploy --app moneymaneger --prod
```

A Flutter restart alone cannot apply Deno changes.

---

# 72. HOW TO HANDLE BUSINESS-SCOPED DATA

Never assume the user only has one Business.

Every Business financial operation must remain correctly scoped to the current Business.

Do not accidentally query or write by UID when the required scope is:

```text
Business ID
```

Always respect the existing active Business architecture.

---

# 73. HOW TO HANDLE ACCOUNT-SCOPED DATA

Not everything belongs to the active Business.

Examples:

```text
Received Invitations
Saved accounts
authentication/profile
```

are account-level concepts.

Do not incorrectly attach them to `activeBusinessId`.

---

# 74. SECURITY RULE OF THUMB

Do not grant broader permissions just to make UI work.

For example, actor name lookup failing did NOT mean everyone should gain:

```text
members.read
```

The correct solution was to define the narrow server-side authorization needed for actor lookup.

Always solve authorization at the minimum necessary privilege.
