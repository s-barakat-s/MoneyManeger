# 1. Current Project Architecture

The application is a Flutter application using:

* Flutter
* Riverpod 3
* GoRouter
* Freezed
* Firebase Authentication
* Cloud Firestore
* Repository-based data access
* `BusinessDataScope` for Business-scoped data
* Deno HTTP backend for operations that require trusted server-side execution

Business data is primarily scoped beneath:

```text
businesses/{businessId}
```

User profile data is stored separately under:

```text
userProfiles/{uid}
```

The old:

```text
users/{uid}
```

hierarchy is obsolete and must not be treated as the active user-profile schema.

---

# 2. Business Backend Migration Context

The project previously depended on Firebase callable Cloud Functions for several Business operations.

The Firebase Functions were Firebase v2 callables deployed/configured around:

```text
europe-west1
```

Operations analyzed included workspace, invitation, member, activity, and identity-related functionality.

A key architectural conclusion was:

> Moving everything directly from Firebase Functions to client-side Firestore is NOT a safe drop-in migration.

Some operations require trusted backend authority because Firestore Rules alone cannot safely reproduce all existing authorization and data-integrity guarantees.

Examples include operations involving:

* membership authorization
* private profile access
* Business owner protection
* canonical/system roles
* invitation recipient identity
* Activity integrity
* username → email resolution

Therefore the migration strategy is:

```text
Flutter client
    ↓
Repository abstraction
    ↓
Deno HTTP API where trusted authority is required
    ↓
Firebase / Firestore
```

rather than blindly replacing every callable with direct Firestore reads/writes.

---

# 3. Important Data Model Findings

The active profile hierarchy is:

```text
userProfiles/{uid}
```

An obsolete callable implementation was found reading:

```text
users/{uid}
```

This is inconsistent with the current schema and Firestore Rules.

Therefore username/email resolution must NOT simply be migrated by copying the old implementation.

Longer-term architecture may require concepts such as:

* Business-scoped member profile projections
* recipient-safe invitation denormalization
* caller-owned workspace projections or carefully constrained collection-group access
* immutable/versioned system roles
* deterministic Activity linkage
* redesign/removal of username login where necessary

These are architectural concerns and must not be changed casually while fixing unrelated bugs.

# 6. Exact Failure That Was Investigated

The application appeared to work immediately after the Phase 1 workspace migration.

The Business could be created/opened successfully.

However, after FULLY closing the application and starting it again, Business workspace resolution failed.

Runtime inspection showed that after restart the application executed:

```text
CallableBusinessWorkspaceRepository
    ↓
httpsCallable('resolveMyBusinessWorkspaces')
```

It did NOT execute:

```text
HttpBusinessWorkspaceRepository
    ↓
GET /api/workspaces
```

Therefore:

```text
workspaceResolutionProvider
```

was still reaching the obsolete Firebase callable implementation after a cold restart.

---

# 7. Root Cause

This was NOT a source-code regression.

This was NOT a Deno backend failure.

This was NOT a Firestore data issue.

This was NOT a production-data issue.

The root cause was an OLD INSTALLED APK.

The Phase 1 migration had been introduced into the currently running Flutter process through hot reload/hot restart behavior, but the installed Android application artifact itself had not been rebuilt with the new source.

The installed APK was inspected.

Its:

```text
kernel_blob.bin
```

contained references to:

```text
resolveMyBusinessWorkspaces
CallableBusinessWorkspaceRepository
```

The installed APK did NOT contain the expected Deno HTTP workspace implementation information such as the Deno hostname / workspace HTTP route.

Therefore the physical APK installed on the device was from the pre-migration implementation.

---

# 8. Why It Worked Before Closing the App

This explains the seemingly contradictory behavior.

The successful process was:

```text
PID 26774
```

That running process contained the hot-reloaded Phase 1 Deno migration.

Therefore it successfully:

* created/opened the Business
* resolved the workspace through the migrated implementation

But when the application was fully terminated:

```text
PID 26774
```

was destroyed.

On the next launch Android started:

```text
PID 30603
```

from the APK physically installed on the device.

That APK was old.

Therefore the application restored:

```text
CallableBusinessWorkspaceRepository
→ resolveMyBusinessWorkspaces
```

instead of:

```text
HttpBusinessWorkspaceRepository
→ GET /api/workspaces
```

This is why:

```text
Hot-loaded process = works
Cold restart = fails
```
