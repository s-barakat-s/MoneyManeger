# 1. PROJECT OVERVIEW

المشروع اسمه:

**Money Manager**

وهو Flutter application لإدارة البيانات المالية.

التقنيات الأساسية:

* Flutter
* Dart
* Firebase Authentication
* Cloud Firestore
* Riverpod
* GoRouter
* Freezed
* JSON Serialization

التطبيق حاليًا:

**Pre-production**

أي:

* لم يتم إطلاقه للمستخدمين الحقيقيين.
* لا توجد production data مهمة.
* لا توجد production users يجب الحفاظ على schema قديمة من أجلهم.

# 3. CORE MULTI-USER PRINCIPLE

كل شخص حقيقي له:

```text
Firebase Auth User
        │
        │ UID
        ▼
User Profile
        │
        ▼
Business Membership
        │
        ▼
Business
```

مثال:

```text
Mahmoud
Firebase UID = uid_1

Ahmed
Firebase UID = uid_2

Youssef
Firebase UID = uid_3
```

الثلاثة يمكن أن يعملوا على:

```text

```

لكن كل واحد يحتفظ بهويته المستقلة.

وبالتالي نقدر نعرف:

```text
Ahmed created transaction X

Mahmoud updated transaction X

Youssef created payment Y
```

# STEP 1 — BUSINESS MEMBERSHIP FOUNDATION

## STATUS

**COMPLETED**

تم تحويل BusinessMember إلى membership حقيقية بين User وBusiness.

الشكل الحالي:

```text
BusinessMember

uid: String
roleId: String
status: MembershipStatus

joinedAt: DateTime?
invitedAt: DateTime?
invitedBy: String?

createdAt: DateTime?
updatedAt: DateTime?
```

---

## Membership Status

الحالات:

```text
invited
active
suspended
removed
```

### invited

تمت دعوة الشخص ولكن لم يصبح عضوًا فعالًا بعد.

### active

عضو فعال.

### suspended

عضويته موجودة لكن الوصول متوقف مؤقتًا.

### removed

لم يعد عضوًا لكن record الخاص به لا يتم حذفه حتى نحافظ على التاريخ.

---

## Role Reference

BusinessMember لا يحتوي:

```text
isAdmin
isOwner
```

بل:

```text
roleId
```

مثال:

```text
roleId = owner
roleId = accountant
```

---

## Owner Bootstrap

العضو الأول:

```text
businesses/{businessId}/members/{ownerUid}
```

ويتم إنشاؤه:

```text
uid = authenticated UID
roleId = owner
status = active
```

# BusinessAccess

تم إنشاء authorization abstraction.

Concept:

```text
BusinessMember
      ↓ roleId
BusinessRole
      ↓
permissions
      ↓
BusinessAccess
      ↓
can(Permission.x)
```

بدل:

```dart
roleId == "owner"
```

---

# Riverpod Permission Resolution

Flow:

```text
Authenticated UID
        ↓
Active Business
        ↓
BusinessMember
        ↓
roleId
        ↓
BusinessRole
        ↓
BusinessAccess
        ↓
can(...)
```

Inactive/missing/malformed membership:

```text
DENIED
```

---

# Role Storage

Firestore:

```text

```


**idempotent**

يعني التشغيل أكثر من مرة لا:

* يكرر roles
* يمسح custom data
* يعيد ضبط role موجود بلا داعٍ

# STEP 3 — INDEPENDENT MEMBER IDENTITY

## STATUS

**COMPLETED**

كل human member أصبح معتمدًا على Firebase UID الخاص به.

---

# Canonical Actor Identity

الـUID هو الهوية الرسمية لأي actor.

Flow:

```text
Firebase Auth UID
        ↓
requireAuthenticatedActorUid(...)
        ↓
authenticatedActorUidProvider
        ↓
repository actingUid
```

Repositories لا تستدعي FirebaseAuth عشوائيًا.

Actor identity يتم inject لها.

---

# Important Business ID Fix

تم إزالة الاعتماد الطبيعي على:

```text
currentUser.uid == businessId
```

الـactiveBusinessId يمكن أن يكون Business آخر بشرط أن المستخدم لديه active membership فيه.

UID == Business ID مازال فقط في:

**deterministic initial bootstrap**

وده مهم جدًا لدعم:

```text
User A → Business X
User B → same Business X
```

وكذلك مستقبلًا:

```text
User A → Business X + Business Y
```

---

# UserProfile vs BusinessMember

المفهومان منفصلان.

UserProfile:

```text
human/account identity
```

BusinessMember:

```text
relationship with Business
```

لا يتم تخزين permissions أو membership status داخل UserProfile.

# Atomic Logging

كل financial write حاليًا يعمل:

```text
Financial Write
+
Activity Log
```

atomically.

يعني لا يحدث:

```text

لكن log ضاع
```

أو:

```text
Log says created
لكن transaction failed
```

# Repayment Activity

Repayment transaction يحتفظ بـatomicity:

```text

+
Debt/Receivable balance update
+
Generated Transaction
+

```

تم تجنب noisy duplicate logs لنفس user action.

# Firestore Security Current Rule

Normal financial operation requires:

```text
Authenticated
+
Active BusinessMember
+
Required Permission
+
Valid Audit Attribution
```

```text

AND
hasPermission("transactions.create")
AND
createdBy == request.auth.uid
AND
correct server timestamp
```

# Invitation Flow


* قبول دعوة تخص email/user آخر

نحدد بوضوح:

أي records يمكن:

```text
update
archive
restore
```

وأي financial operations الأفضل لها:

```text
correction
reversal
```

بدل تعديل التاريخ المالي مباشرة.

خصوصًا:

* transfers
* payments
* financial transactions

# STEP 12 — SCHEMA VERSIONING

لدينا أصلًا concept:

```text
schemaVersion
```

في Business.

لاحقًا نحتاج formalize:

```text
currentSchemaVersion
```

وفصل:

```text
App Version
```

عن:

```text
Data Schema Version
```

# STEP 13 — MIGRATION FRAMEWORK

بعد ما التطبيق يبقى production، لا يمكننا تغيير schema بحرية كما نفعل الآن.

نحتاج architecture مثل:

```text
Migration
MigrationRunner

v1_to_v2
v2_to_v3
...
```

ويجب أن migrations تكون:

* idempotent
* resumable/safe
* non-destructive قدر الإمكان

---

# STEP 14 — BACKWARD-COMPATIBLE MODELS

بعد production:

إضافة field جديدة لا يجب أن تجعل client قديم أو data قديمة تنهار.

نحتاج:

* safe defaults
* optional new fields
* tolerant enum parsing
* unknown permission tolerance
* version-aware parsing عند الحاجة

بعض الأساس موجود بالفعل، مثل unknown permissions handling.

---

# STEP 15 — DATA LAYER HARDENING

نراجع أن كل Firestore access يمر عبر:

```text
repositories
data scopes
path helpers
```

ولا يوجد feature يبني Firestore paths عشوائيًا.

الهدف:

سهولة تغيير storage/schema مستقبلًا.

---

# STEP 16 — VALIDATION / REFERENTIAL INTEGRITY

تقوية validation مثل:

* valid amounts
* valid owner IDs
* valid debt IDs
* valid references
* valid Business scope
* valid enums
* cross-document invariants المهمة

# STEP 17 — ARCHIVING STANDARD REVIEW

الأساس موجود بالفعل.

لكن نراجع أن كل persisted financial entities تتبع نفس lifecycle policy.

الهدف:

لا يوجد feature يعمل hard delete بينما الباقي archive بدون سبب.
